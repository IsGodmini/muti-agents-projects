# 01｜项目背景与业务需求

## 1. 项目背景

个人用户在规划旅行时，通常需要在多个平台之间反复切换：搜景点、查门票、看地图估距离、排时间、算预算。一趟 3 天旅行的攻略可能需要花 3-5 小时整理，而且结果往往粗糙——时间冲突、路线折返、预算超支。

TripOps AI 是一个面向个人用户的 Web 对话式旅行策划助手，并保留 CLI 调试入口。用户用自然语言描述需求，系统在收集出发时间等必要信息、询问额外注意事项并获得明确确认后，才会执行资源搜索、路线优化、行程编排、成本估算、质量检查和交付物生成。

## 2. 目标用户

- **家庭出游**：带孩子旅行的家长，需要控制活动强度、安排休息时间。
- **朋友结伴**：小团体出行，需要兼顾不同兴趣和预算。
- **银龄旅行**：为长辈安排低强度、节奏舒适的慢游行程。
- **个人出行**：想快速拿到一份靠谱攻略的自由行用户。

## 3. 交互方式

Web 页面提供单一对话入口，由 LLM 主导提问：

1. 用户用一句话描述旅行想法（如"暑假想带孩子去北京玩几天"）。
2. Agent 追问目的地、出发时间、天数、人数/客群和预算等必要信息。
3. 必要信息齐全后，Agent 单独询问其他注意事项或需要避免的情况。
4. Agent 展示结构化需求摘要；只有用户明确确认后才自动开始策划，不能通过“开始吧”绕过确认。
5. 页面只展示当前正在执行的节点及其活动；节点结束后切换到下一节点，全部结束后隐藏当前节点状态。
6. 方案通过质量检查后等待用户批准；批准生成 PDF 与 Markdown，驳回则记录决定。

没有直接生成表单，所有需求均来自自由文本并结构化为 `PlanRequest`。对话图按 `collecting → notes → confirming → ready` 推进，策划接口只接受已经 `ready` 的会话，旧的直接运行接口已删除。

## 4. 业务流程

1. **需求收集与确认**（chat_graph / LLM）：收集必要信息、询问注意事项、展示摘要并等待明确确认，输出结构化 `PlanRequest`。
2. **资源检索**（Tavily MCP + 高德 POI 双路）：实时搜索目的地景点/活动网页，同时通过高德获取结构化 POI（坐标、评分、分类）。
3. **防护与充实**：Guard 过滤注入风险内容；LLM 多模态估算票价、时长、分类和开放时间，并可选结合搜索图片判断实况。
4. **评分排序**（确定性）：按兴趣匹配、质量、必去加分、预算/拥挤/天气惩罚计算综合分。
5. **交通估算**（高德实测 + LLM 估算）：有坐标时优先使用高德，缺失的交通对由 LLM 补齐；调用失败会保留明确错误。
6. **路线优化**（OR-Tools）：求解访问顺序并生成与请求天数完全一致的日槽；资源不足的日期进入自由活动/休整补全。
7. **行程编排**（LLM）：和风天气优先、高德天气降级，逐日生成含午餐和休息的时间表。
8. **约束校验**（确定性规则）：检查行程天数覆盖、空日程、重复资源、时间冲突、每日跨度、午餐、必去覆盖等。
9. **应急替代**：约束不满足时最多进行 2 次约束修复；质量/验证失败另有最多 2 次审核修复。
10. **成本估算**（LLM + 计价工具）：过滤零金额明细；全部为零时生成非零保守估算，再计算售价与毛利。
11. **质量审核**（LLM + 确定性校验）：多维评分 + 9 项确定性检查，天数不完整属于阻断问题。
12. **图片与交付物**（ComfyUI + 真实图片降级 + ReportLab）：按普通设备能力顺序生成封面和每日插图；PDF 是带图的精简矢量版式，Markdown 是不嵌图的详细执行与审核报告。
13. **人工确认**：`approval_gate` 节点调用 `interrupt()` 暂停，CLI/API 提交审批决定后恢复，批准进入交付、驳回记录决定。
14. **方案存档**：版本快照、审批记录、交付文件和图片资产持久化到本地目录。

若策划最终失败，系统不会交付不完整文件；SSE 返回失败节点和用户可读原因，前端恢复对话输入，引导用户调整需求后重试。

## 5. 为什么不用单个 Prompt

一个大 Prompt 可以生成"看起来完整"的行程，但：

- 景点信息是模型记忆，不是实时搜索，可能过时或编造。
- 路线顺序凭感觉，没有算法优化，容易折返。
- 成本是编的数字，不是基于实际票价的估算。
- 无法在约束失败时自动搜索替代方案。

多 Agent + 实时搜索（Tavily/高德）+ 算法优化（OR-Tools）+ 确定性约束校验的组合，让方案真实、可执行、可验证。
