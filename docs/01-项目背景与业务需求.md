# 01｜项目背景与业务需求

## 1. 项目背景

旅行社、目的地运营商和企业差旅团队经常需要把一段模糊需求转成可售卖的文旅产品。输入可能只有目的地、日期、人数、预算和偏好，交付物却包含行程、交通、住宿、成本、风险提示、营销文案与宣传海报。

传统流程通常由产品经理在多个网站、表格和聊天工具之间切换，存在三个核心问题：

1. 信息分散：景点开放时间、距离、价格和适用人群来自不同数据源。
2. 决策耦合：路线变化会连锁影响用车、酒店、餐饮和报价。
3. 交付不稳定：不同策划人员的模板、核验标准和文案质量差异明显。

TripOps AI 将该流程建模成多个有明确职责、共享状态和质量关卡的 Agent，由 LangGraph 负责调度。模型负责理解与生成，工具负责查询和计算，技能负责固化业务方法，人工负责最终决策。

## 2. 目标用户

### 文旅产品经理

- 输入客户需求，快速获得第一版方案。
- 查看路线、成本和风险证据。
- 修改约束并重新生成。

### 运营与销售

- 将已审核方案转成对客文案。
- 选择产品卖点并生成宣传海报。
- 导出可继续编辑的交付内容。

### 审核人员

- 检查预算、资源可用性和高风险事项。
- 对方案批准、驳回或提出修改意见。
- 保留版本和操作记录。

### 平台管理员

- 管理 Agent 可调用的工具与技能。
- 配置模型路由、超时、权限和成本上限。
- 观察工作流运行质量。

## 3. 典型业务流程

以“为 6 人家庭设计成都 4 天 3 晚文化美食产品，预算每人 3500 元”为例：

1. 需求理解：抽取硬约束和软偏好，识别缺失字段。
2. 资源检索：查找景点、酒店、餐饮与交通候选项。
3. 行程设计：组合每日活动，控制时间窗和体验节奏。
4. 路线优化：计算移动成本，避免不合理折返。
5. 成本核算：形成单项成本、总价、毛利和价格敏感项。
6. 风险质检：检查闭馆、超预算、时间冲突和信息时效性。
7. 人工审批：审核人员批准或要求返工。
8. 内容交付：生成产品摘要、营销文案和目的地宣传海报。

## 4. 为什么采用多 Agent

单个大 Prompt 可以生成“看起来完整”的行程，但难以稳定保证：

- 行程中的每个资源都能追溯到证据。
- 预算变化后，报价和路线同步更新。
- 高风险动作在执行前经过审批。
- 不同类型任务使用适合的模型，控制速度和成本。
- 某一环节失败时，只重试局部节点而不是重新生成全部内容。

多 Agent 在本项目中不是让多个聊天机器人自由对话，而是把复杂业务拆成可测试的节点，通过统一状态和条件边确定执行顺序。

## 6. 非功能需求

### 可控性

- 高风险工具必须声明风险级别。
- 最终发布和外部写操作必须经过人工审批。
- Agent 输出尽可能采用结构化 Schema。

### 可追溯性

- 保存工作流 thread_id、节点状态、工具调用和方案版本。
- 关键事实关联来源、抓取时间和置信度。
- 生产环境应记录 Prompt 版本与模型版本。

### 可恢复性

- 长流程通过 checkpoint 保存状态。
- 可重试节点应与不可重复的外部写操作分离。
- 写操作使用幂等键避免重复提交。

### 性能与成本

- 轻量模型承担分类、抽取和校验任务。
- 较大模型处理跨资源综合规划。
- 视觉模型仅在图片理解场景启用。
- 海报生成放在审批后的最终交付阶段。

## 7. 项目范围

当前项目包含：

- 文旅需求录入与策划结果展示。
- 多 Agent 工作流及人工审批。
- 演示资源检索、路线优化、成本计算和质检。
- 模型、工具、技能与数据层的扩展接口。

当前项目不承诺：

- 真实预订、支付、出票和退款。
- 对第三方库存、开放时间和价格的实时正确性负责。
- 自动发布营销内容到公共渠道。
- 无人工审核的商业报价。

## 8. 验收标准

一个完整演示应满足：

1. 用户可创建一个包含核心约束的策划任务。
2. API 返回稳定的结构化方案，并包含每日行程、成本与风险。
3. 工作流能在审批节点暂停，并使用同一 thread_id 恢复。
4. 页面可以展示工具、技能及整体架构。
5. 自动化测试覆盖图执行、工具调用和关键页面内容。
6. 文档能清楚区分已实现能力与生产化规划。
