# 08｜本地开发与部署

## 1. 前置要求

轻量开发模式需要：

- Node.js 20+
- npm
- Python 3.11+
- uv

完整依赖模式还需要：

- Docker 与 Docker Compose
- Ollama（真实模型模式）
- 可选的文生图服务

## 2. 前端启动

```bash
npm install
npm run dev
```

访问 `http://localhost:3000`。

常用命令：

```bash
npm run build
npm run lint
node --test tests/rendered-html.test.mjs
```

## 3. 后端启动

```bash
cd backend
uv sync
uv run uvicorn app.main:app --reload --port 8000
```

访问：

- 健康检查：`http://localhost:8000/api/v1/health`
- Swagger：`http://localhost:8000/docs`

检查与测试：

```bash
uv run ruff check app tests
uv run pytest -q
```

## 4. 环境变量

先复制示例文件：

```bash
cp .env.example .env
```

常见配置类别：

| 变量类别 | 用途 |
| --- | --- |
| 数据库 URL | PostgreSQL/PostGIS/pgvector 连接 |
| Redis URL | 缓存和 Celery Broker |
| Ollama Base URL | 本地模型服务地址 |
| Model Names | 4B、8B、VL 模型路由 |
| Poster Provider | `mock` 或真实文生图适配器 |
| Poster Endpoint/Key | 文生图服务地址与凭证 |
| Tavily MCP | Remote MCP 地址、API Key、搜索深度、超时与降级开关 |

不要提交真实密钥。生产环境使用密钥管理服务注入。

## 5. Tavily MCP 真实搜索

在 Tavily 控制台创建 API Key，然后配置：

```env
TAVILY_SEARCH_ENABLED=true
TAVILY_MCP_URL=https://mcp.tavily.com/mcp
TAVILY_API_KEY=tvly-your-key
TAVILY_SEARCH_DEPTH=advanced
TAVILY_SEARCH_TIMEOUT_SECONDS=30
TAVILY_FALLBACK_TO_DEMO=false
```

后端通过 MCP Streamable HTTP 调用远程 `tavily_search` Tool。生产环境建议关闭演示降级，这样搜索失败会明确终止资源研究节点，而不会把演示资源混入正式方案。

健康检查只返回是否已配置，不返回密钥：

```bash
curl http://localhost:8000/api/v1/health
```

## 6. Ollama 模型准备

安装 Ollama 后拉取模型：

```bash
ollama pull qwen3:4b
ollama pull qwen3:8b
ollama pull qwen3-vl:4b
```

确认服务：

```bash
ollama list
```

模型体积和显存需求取决于具体量化版本。开发时可只启动当前节点需要的模型。

注意：默认演示工作流不依赖模型即可运行。要让主流程真实调用模型，需要把 Agent 节点接入 `ModelGateway`，并补充结构化输出验证与回退策略。

## 7. Docker Compose

在项目根目录执行：

```bash
docker compose up --build
```

配置包含前端、API、PostgreSQL 和 Redis。数据库初始化脚本会启用 PostGIS/pgvector 并创建业务表。

仅检查 Compose 配置：

```bash
docker compose config
```

首次构建需要下载基础镜像和依赖；受限网络环境下应配置镜像源或在联网环境预构建。

## 8. 文生图服务

开发默认使用：

```env
POSTER_PROVIDER=mock
```

接入真实服务时：

1. 实现或配置统一 Adapter。
2. 提供 endpoint、模型名和密钥。
3. 将长耗时生成任务放入异步队列。
4. 保存 prompt_version、seed、方案版本和资产 URL。
5. 设置超时、内容安全审核和失败重试上限。

海报失败不应让已经批准的行程数据丢失。

## 9. 推荐开发顺序

1. 先运行前端测试和后端测试。
2. 使用 Mock 模式完成一次审批流程。
3. 启动 PostgreSQL/Redis，替换内存存储。
4. 接入 `qwen3:4b` 的需求抽取节点。
5. 接入 `qwen3:8b` 的复杂规划节点。
6. 最后接入视觉理解和文生图。

这种顺序便于定位问题来自业务图、数据层还是模型。

## 10. 常见问题

### 审批 thread_id 无法恢复

演示版使用内存 checkpoint。确认创建与审批请求命中同一个后端进程，并且进程没有重启。

### Ollama 在 Docker 中无法访问

容器内的 `localhost` 指向容器自身。macOS/Windows 可尝试使用 `host.docker.internal`，Linux 需配置宿主机网关。

### pgvector 维度错误

确认嵌入模型的输出维度与数据库 `vector(1024)` 一致。更换模型后需迁移字段或重建向量。

### 海报生成很慢

将任务放入 Celery，API 返回任务 ID；前端轮询或订阅进度。不要让长图像任务占用同步请求。
